## yfsp: extractStreamUrl returned none

### Root cause

The play endpoint (https://m10.yfsp.tv/v3/video/play) intermittently fails
with:

- biz code 5 ("fang wen guo liang", per-IP rate limit): the old code retried
  exactly once, immediately, then gave up.
- non-JSON / edge error pages: resp.json() threw and the catch returned
  {streams:[]} silently, with no diagnostic log.

Either condition produces "0 streams from module". Live re-test on 2026-08-22
showed the API healthy for both request shapes (a=0 episode-keyed and a=1
movie-keyed both return flvPathList incl. HLS chunklist), confirming a
transient-failure handling gap rather than a broken flow.

### Fix (v1.0.3) - yfsp/yfsp.js

1. New playApiCall(): defensive GET+parse; HTML/non-JSON bodies become
   retryable errors instead of silent empties.
2. extractStreamUrl() now tries up to 3 attempts per key shape, then falls
   back from the episode key (a=0) to the movie key (a=1), which hits a
   different rate-limit bucket.
3. Every dead end is logged ([YFSP] play attempt n/3 ..., final give-up line)
   so in-app logs.txt shows why streams came back empty.
4. parsePlayData() gained a clarity[].path.result fallback for responses
   where flvPathList is empty but quality tiers carry playable chunklists.

Verified: search 1 / details OK / 1176 episodes / 1 HLS stream, chunklist
verifies HTTP 200 application/vnd.apple.mpegurl.

## allmanga: stream URL returns an HTML error page (HTTP 200)

### Root cause chain

1. Bundled FALLBACK_KEYGEN was build 114 / epoch 2954; the platform rotated to
   build 136 and answers AA_CRYPTO_STALE to tokens built with old keys.
2. The remote keygen repo (anipy-cli) still served build 81, so the
   never-downgrade guard correctly rejected it; decryption impossible.
3. With the encrypted episode query failing, the module fell back to
   aaLegacyStreams(), which fabricates https://allmanga.to/data.../N.mp4 style
   URLs. Those return the site HTML shell with HTTP 200 - exactly what the
   checker flagged ("on allmanga.to").

### Fix (v1.9.0) - allmanga/allmanga.js

1. Fresh snapshot: build 136 / epoch 2955 / key deeb2732...5da
   (captured live 2026-08-22; partB + mask cross-checked).
2. NEW self-bootstrap: on AA_CRYPTO_STALE / MISSING / EXPIRED (or when a
   tobeparsed body fails to decrypt) the module now derives fresh keys itself,
   pure JS, no third-party dependency:

     embed[i] = concat(base64decode(AA_MASK_BLOCKS))            [32 bytes]
     salt[i]  = (buildId.charCodeAt(i %% len) || 0)
                ^ ((i * 78 + 200) & 255)
     lin[i]   = (((i >> 3) * 234) + ((i %% 8) * 70)) & 255
     mask[i]  = embed[i] ^ salt[i] ^ lin[i]
     hmacKey  = HMAC-SHA256(mask, "qrSOLsg:" + buildId)
     bootTok  = hex(HMAC-SHA256(hmacKey,
                    "<epoch>~mkissa.to~<lane>~mkissa~<buildId>"))
     GET api.mkissa.net/client-crypto/v1/bootstrap?buildId=<id>&k=<lane>
       headers: x-build-id, x-aa-boot=<bootTok>, Referer https://mkissa.to/
     key      = first32(base64decode(partB)) XOR mask

   Implemented as aaBuildMask() + aaHmacSha256() (RFC 2104 over the existing
   aaSha256) + aaBootstrapFor()/aaFetchRemoteKeys(lane). Epochs are 7-day
   (floor(now/604800000)); during the first day of an epoch the previous one
   is still accepted. The remote anipy-cli keygen remains as last-resort only.
3. aaResolveTranslation() retries the query after a successful refresh and
   also re-bootstraps once when decryption of a present tobeparsed body fails
   (mirrors the site rk()).

Verification evidence (2026-08-22):
- Client mask reproduced byte-exact vs live capture:
  34fcbcf927c4628c34ed1fd2068b8131f4f29136adcd61e28b4b8fa7bc59024f
- HMAC implementation matches RFC 4231 test vector.
- Key derived from captured partB equals the browser-captured key
  (deeb2732190ceee0d84c7668d79b64ddcd5f27b9f858f2327fe29a7841b7b5da).
- End-to-end via harness: search 5 / details OK / 1181 episodes / 2 streams
  (SUB + DUB HLS), both verify HTTP 200 application/vnd.apple.mpegurl.
- Note: api.mkissa.net sits behind Cloudflare which challenges curl/node-undici
  TLS fingerprints intermittently; the Sora app network stack and real browsers
  pass. A local 403 HTML on bootstrap is environmental, not a module bug.

Keygen scheme changes documented in documentation/keygen-live-capture-prompt.md
(build 136 section: weekly epochs, tilde-joined boot message with new part
order, qrSOLsg: prefix, per-content lanes k7/k9/k2).

## Deferred (per user decision): fix later

### allmanga-novels (mangas contract)

Findings from this audit, to apply when picked up again:

1. Same stale-keygen failure as the anime module: FALLBACK_KEYGEN must be
   updated to the build 136 snapshot above AND chapterPages queries must use
   lane **k9** (the API enforces per-content lanes; episode=k7,
   chapterPages=k9, music=k2). The current module hardcodes lane k7 everywhere,
   so tokens would fail even with fresh keys. Port the self-bootstrap flow
   (aaLiveKeys equivalent) with lane parameterised per query type.
2. Checker-contract mismatch (probable cause of "no search results" errors
   despite search passing): the module returns kanzen mangas contract objects
   ({id,title,imageURL}) while server.js-style video checkers read first.href;
   details/episodes/stream steps then abort. When fixing, either register it
   with a manga-aware checker or emit href/image aliases alongside id/imageURL.

### comix (X-Scramble API)

Status as of 2026-08-22 (deep dive; module patched to v1.1.3):

1. **The site origin is down** (Cloudflare serves 502 Bad gateway on comix.to
   AND comix.ws even to a real Chrome that passes the managed challenge).
   Nothing client-side can fetch data during the outage.
2. **Transport layer**: Cloudflare managed challenges block curl, node-undici,
   Google Apps Script relays, Jina Reader and allorigins alike ("Just a
   moment..."). A real browser passes the challenge (we observed challenge ->
   502), which means pass/fail is IP+TLS-reputation based - exactly like
   AllManga: the Sora app network stack should pass where flagged server IPs
   fail.
3. **Corroborating implementation**: yurtzy/comix-api (Feb 2026) hits
   `/api/v1/manga` as PLAIN JSON with browser-spoof headers only (no signature)
   for search/browse, uses a VM-run `secure-*` chunk with a per-page
   `meta[name=cfg]` token only for chapter-page decryption. Their public
   deployment now also fails with "Source blocked by Cloudflare bot
   protection" - confirming datacenter IPs got cut off after Feb 2026.
4. **Module v1.1.3 changes** (mirrors the AllManga resilience pattern):
   - multi-host fallback array (comix.to -> comix.ws) in apiGet();
   - full browser-grade header set (Accept-Language / Cache-Control / Pragma /
     Upgrade-Insecure-Requests / Referer + current Chrome UA);
   - failure classification in logs ("cloudflare challenge" vs "origin down
     (502)" vs "html response") instead of a bare parse error;
   - X-Scramble `_` token generation and `{"e":...}` decryption unchanged
     (token self-test passes; constants not yet re-verifiable while origin is
     down - re-check against the live API when it returns, see the
     secure-tgambp-7QDhTKTL.js reference chunk in yurtzy/comix-api).
